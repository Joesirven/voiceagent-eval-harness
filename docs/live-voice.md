# Live voice

The browser live-voice path captures microphone audio, sends it through a WebSocket, and receives agent audio. A direct model adapter or a Pipecat orchestration module can own the session.

The client converts microphone input to the format required by the selected voice module. Voice activity detection controls turn completion and barge-in. The trace records only the spoken part of an interrupted agent turn.

The server binds to a loopback address by default. It rejects non-loopback browser origins. It also refuses a second session when one call is already active.

Live providers need credentials and can incur cost. Keep their values outside the repository. Use text and mock voice modules for deterministic tests.

## Voice errors

Every failure on the voice paths (direct Azure, Pipecat, Deepgram, and the Python helpers under `src/orchestration-modules/pipecat/`) has a fixed code in one catalog, `src/server/voice/voice-errors.ts`: a plain title, what happened, a concrete fix, a severity (`error` or `warning`) and whether the call can continue. `reportVoiceError(code, ...)` is the one way an error is emitted. It never carries a key, a hostname or provider text; an unknown code becomes `voice_unknown_error`.

- **Where it shows.** A `voice_error` trace event on the call's trace (when the call is traced), the `voiceErrors` list in `GET /api/state` (the 20 most recent, newest last, including errors outside any call such as a failed selection), and an `error` frame on the browser voice socket with the same fields. The shape is in `docs/interfaces.md`.
- **What blocks new calls.** Only an Azure-not-working failure: Azure refusing the key (`azure_auth_failed`), a missing deployment (`azure_deployment_not_found`), Azure not reachable after the one retry (`azure_connect_failed`; a network blip clears itself on the next passing check), or missing or invalid Azure settings (`azure_env_*`, `azure_live_url_*`). These call the existing Azure block (`markAzureFailed` in `src/server/azure-startup-check.ts`), so the next `POST /api/play/start` answers 503 `azure_unavailable`, `azureStatus` shows the reason, and the block lifts when the check passes again (at most every 5 seconds). They are detected from the websocket handshake status (`src/server/voice/manager.ts`), from Azure error events in a call (`classifyAzureError` in `src/modules/azure-live-session.ts`, which reads only the code, type and status fields), and from the Deepgram helper's Azure reply. Everything else (Pipecat, Deepgram, a rate limit, a timeout, a dropped connection in a call, no microphone audio) only notifies.
- **Retries.** A start that fails for a passing reason (`azure_connect_failed`, `azure_start_timeout`, `azure_closed_before_start`, `pipecat_failed`, `pipecat_closed`, `deepgram_failed`, `deepgram_start_timeout`, `deepgram_closed`, `protocol_error`) is tried once more with a fresh session, 400 milliseconds later; the first failure is recorded as a warning that says it is trying once more, and the browser socket stays open. If the retry fails too, the call ends once with the error record. A Pipecat helper that crashes in the middle of a call is restarted once while the call stays open (the relay keeps no conversation state; Azure does); a second crash ends the call. A dropped Azure connection or a crashed Deepgram helper in the middle of a call is not retried, because the conversation state lives there; the call ends with the notification.
- **Ending a call.** Only an error that truly stops the call ends it (the Azure connection closed, a helper that cannot be restarted, the start failing twice). Warnings, such as no microphone audio after 8 seconds, leave the call running. New calls are always allowed, except while the Azure block is on.
